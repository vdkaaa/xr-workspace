El web client actual NO usa el WebSocket bridge (wsService.js). Dónde entra Unity WebGL

Unity WebGL corre dentro del navegador, en el mismo origen/sandbox que el web client. Tiene dos caminos posibles para hablar con el resto del sistema (ambos ya existen en el backend, pero solo uno tiene forma de "protocolo" definida hoy):

  1. REST + x-room-token — igual que el web client: login con Supabase, POST /api/rooms/:id/join, y de ahí usar el roomToken para crear/mover/borrar objetos espaciales y pedir token de voz.
  2. WebSocket bridge (ws://.../?token=...&room_id=...&user_id=...) — conexión directa al servidor ws del backend, que reenvía mensajes a otros clientes conectados a la misma sala y los reenvía también como evento de Liveblocks (broadcastEvent, no Presence/Storage).

Reglas reales de asignación de rol en joinRoom

  • Al crear una sala, el creador queda con rol owner en room_members (createRoom).
  • Si la sala es pública y el usuario no era miembro: se le asigna editor automáticamente (hardcodeado — no hay lógica de "viewer por defecto").
  • Si la sala es privada: el usuario debe ya existir como fila en room_members (invitado previamente); si no, 403. Si existe, se reusa su role actual tal cual está en la BD.
  • Rate limit: authLimiter — 10 requests por IP cada 15 min (mismo limiter que login/register).

Estructura EXACTA del JWT roomToken

// Payload real (jwt.sign), backend/src/services/roomService.js líneas 222-226 y 259-263
{
  "sub": "b3f1e2a0-....",     // user.id de Supabase
  "room_id": "8a1e....-room", // UUID de la sala
  "role": "editor",           // "owner" | "editor" | "viewer"
  "iat": 1751000000,
  "exp": 1751028800           // 8 horas (expiresIn: '8h')
}
// Firmado HS256 con process.env.JWT_SECRET

Cómo se valida en cada request (backend)

// backend/src/middleware/auth.js — dentro de requireAuth
const roomToken = req.headers['x-room-token']
if (roomToken) {
  const decoded = jwt.verify(roomToken, process.env.JWT_SECRET)
  if (decoded.sub === req.user.id) {   // debe coincidir con el Bearer token
    req.user.role = decoded.role
    req.user.room_id = decoded.room_id
  }
}
// backend/src/middleware/authorize.js — requireRole(minRole)
const ROLE_RANK = { owner: 3, editor: 2, viewer: 1 }
// pasa si ROLE_RANK[currentRole] >= ROLE_RANK[minRole]
Fuente: backend/src/middleware/auth.js, backend/src/middleware/authorize.js.

3. Protocolo del WebSocket bridge

⚠ Léeme primero

Extraje esto línea por línea de backend/src/services/wsService.js. Hoy es un relay genérico: no existe una lista cerrada de tipos de mensaje (join, move, spatial-object-update, etc. no están implementados como tipos especiales en el código — el servidor no los interpreta, solo los reenvía). El único mensaje con formato fijo que emite el servidor es CONNECTED. Todo lo demás (qué type usar para mover un avatar, sincronizar transform, etc.) es un contrato que todavía hay que diseñar entre Unity y backend. Ver "Preguntas abiertas".

Conexión

// URL de conexión (query params leídos en wsService.js)
wss://<backend-host>/?token=<roomToken_o_access_token>&room_id=<uuid>&user_id=<uuid>

// En local:
ws://localhost:3000/?token=eyJ...&room_id=8a1e...-room&user_id=b3f1...

⚠ El servidor NO valida el JWT en la conexión WS

Código real:

// backend/src/services/wsService.js
if (!token || !roomId) {
  ws.close(1008, 'token y room_id requeridos')
  return
}

Solo verifica que token y room_id existan (no vacíos) — nunca llama a jwt.verify sobre ese token, a diferencia de las rutas REST. Cualquier string no vacío pasa. Esto es una brecha de seguridad real del código actual, no una suposición mía — avisale a Diego antes de que Felipe construya lógica de confianza sobre esta conexión.

Mensaje que el servidor SÍ envía siempre al conectar

// Enviado por el servidor apenas se acepta la conexión
{ "type": "CONNECTED", "data": { "roomId": "8a1e...-room" } }

Formato de mensajes cliente → servidor

Cualquier mensaje enviado por un cliente debe ser JSON con esta forma (es lo único que el servidor espera para poder reenviarlo):

{ "type": "<string libre>", "data": { /* cualquier objeto */ } }

Qué hace el servidor con cada mensaje recibido

// backend/src/services/wsService.js — ws.on('message', ...)
ws.on('message', async (raw) => {
  const { type, data } = JSON.parse(raw.toString())

  // 1) Reenvía el mensaje como "room event" de Liveblocks (broadcastEvent)
  //    Esto NO toca Presence ni Storage — es un canal de eventos efímero aparte.
  await liveblocks.broadcastEvent(roomId, { type, data })

  // 2) Reenvía el mensaje TAL CUAL a los demás clientes WS conectados
  //    a la misma room_id (excepto al que lo mandó)
  broadcastToRoom(roomId, message, ws)
})

Al desconectarse

No se emite ningún mensaje explícito de "disconnect" a los demás clientes. El servidor solo:

  • Quita al socket del Set de la sala
  • Registra un evento leave en Supabase vía trackEvent(roomId, userId, 'leave', { duration_seconds }) (tabla de eventos de sesión)

Si Unity necesita saber cuándo otro peer se desconectó, hoy no hay un evento dedicado — tendría que inferirse (ej. por timeout de "heartbeat" propio, ya que tampoco hay ping/pong de aplicación implementado).

Relación con Liveblocks

broadcastEvent despacha a los listeners de useBroadcastEvent/useEventListener del SDK de Liveblocks — pero el web-client actual no tiene ningún listener registrado (no aparece useEventListener ni useBroadcastEvent en web-client/src). Es decir: hoy, lo que Unity mande por el WS bridge no llega visualmente a nadie hasta que alguien (Diego o Felipe) agregue un listener en el web client o en Unity mismo del lado receptor.

Ejemplo de sesión (formato válido, no un tipo "oficial")

// Cliente Unity → servidor (ejemplo de payload que SÍ pasaría por el relay,
// pero el "type" y las claves de "data" son una propuesta a validar con Diego)
{
  "type": "avatar-transform",

Rooms/estado en memoria

El servidor mantiene un Map<roomId, Set<WebSocket>> en memoria de proceso (variable rooms) — no persiste en Redis ni Supabase. Si el backend reinicia (deploy en Railway) o corre en más de una instancia, las conexiones activas se pierden/no se comparten entre instancias. Importante para diseñar la reconexión en Unity (sección 7).

4. API de Spatial Objects

Schema real de la tabla

-- backend/supabase/migrations/20260602210645_new-migration.sql
CREATE TABLE spatial_objects (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  room_id UUID REFERENCES rooms(id) ON DELETE CASCADE,
  type TEXT CHECK (type IN ('whiteboard', 'file', 'note', 'model')),
  position JSONB DEFAULT '{"x":0,"y":0,"z":0}',
  rotation JSONB DEFAULT '{"x":0,"y":0,"z":0,"w":1}',  -- cuaternión (x,y,z,w)
  scale JSONB DEFAULT '{"x":1,"y":1,"z":1}',
  content_url TEXT,
  metadata JSONB DEFAULT '{}',
  created_by UUID REFERENCES auth.users(id),
  updated_at TIMESTAMPTZ DEFAULT now()
);

⚠ Discrepancia: valores válidos de type

El constraint SQL solo permite 'whiteboard' | 'file' | 'note' | 'model'. Sin embargo, el ejemplo en la documentación Swagger (backend/src/routes/spatialObjects.js) usa "model3d", que violaría el CHECK y la BD rechazaría el insert. Para Unity: usar siempre "model" (no "model3d") hasta que Diego confirme/actualice el constraint.

Busqué spatialObjects.test.js en todo el repo y no existe (solo hay tests para rooms, authorize, sessionEventService y snapshotService). 6. Restricciones de WebGL crítico

Un build de Unity exportado a WebGL corre dentro del navegador, en el mismo sandbox de JavaScript que el web client de React. Esto tiene consecuencias directas:

✅ Funciona igual que en el web client

  • Todas las llamadas REST (fetch/UnityWebRequest) — sujetas al mismo ALLOWED_ORIGINS (CORS) configurado en backend/src/index.js
  • El WebSocket bridge (ws:///wss://) — se conecta al mismo host/puerto que el backend
  • LocalStorage / sessionStorage del navegador (para guardar access_token/roomToken, igual que hace web-client/src/stores/authStore.ts)
  • WebRTC (LiveKit) vía los bindings JS del navegador

❌ NO disponible en WebGL (solo build nativo)

  • Acceso a filesystem nativo del dispositivo
  • APIs nativas de Meta Quest (OpenXR nativo, Passthrough API, hand-tracking nativo, plugins Android/Oculus)
  • Sockets TCP/UDP crudos (Unity WebGL compila los sockets a WebSocket vía Emscripten — no hay UDP real)
  • Multithreading nativo completo (WebGL usa Web Workers con limitaciones)
  • Cualquier plugin nativo (.so/.aar/.dll) sin build especial para WebAssembly

⚠ Sobre CORS/ALLOWED_ORIGINS y el WebSocket bridge — corrección importante

Revisé el código real: cors() con el allow-list de ALLOWED_ORIGINS (backend/src/index.js) se aplica solo a las rutas Express (HTTP). El servidor WebSocketServer de wsService.js está montado sobre el mismo servidor HTTP pero no verifica el header Origin en el handshake — no hay ningún chequeo de origen en ese archivo. Es decir: para las rutas REST, si el build WebGL corre en un dominio no listado en ALLOWED_ORIGINS, el navegador bloqueará la respuesta (falla real de CORS). Para el WebSocket bridge, hoy no hay ese bloqueo — cualquier origen puede conectarse. No asumas que ambos tienen la misma protección; para el REST sí hay que estar en ALLOWED_ORIGINS, para el WS bridge no hay enforcement todavía (ver "Preguntas abiertas").

⚠ Preguntas abiertas para Diego

Todo lo de acá es información que no pude confirmar leyendo el código — decidí listarlo explícitamente en vez de inventar un ejemplo, tal como pediste.

1. Contrato de mensajes del WebSocket bridge

wsService.js es un relay 100% genérico. No existe ningún type de mensaje predefinido (ni move, ni spatial-object-update, ni disconnect) en el código actual — solo CONNECTED que emite el servidor. ¿Cuáles son los tipos de mensaje que Unity debería emitir para sincronizar avatares/transforms en tiempo real? ¿Ese contrato ya está definido en algún ticket de Linear/Jira/Notion que no esté en el repo?

2. Validación de identidad en el WebSocket bridge

El servidor WS no verifica la firma del token recibido por query string, solo que no esté vacío. ¿Es intencional (MVP) o falta implementar jwt.verify ahí también antes de que Felipe construya sobre esto?

3. Cómo un usuario llega a ser "viewer"

No encontré ningún endpoint para invitar usuarios a una sala privada asignándoles un rol específico, ni para cambiar el rol de un miembro existente (no hay PATCH /api/rooms/:id/members/:userId ni similar). joinRoom solo asigna editor (sala pública) o reutiliza un rol que ya debía existir de antes (sala privada). ¿Cómo se crea hoy una fila de room_members con rol viewer? ¿Es manual en Supabase, o falta ese endpoint?

4. Origen del build WebGL: ¿WebXR o build plano?

No hay nada en el repo (ni en unity-client/, vacío salvo el template default de Unity) que indique si el objetivo es un build con WebXR Export (estéreo, en el navegador del visor Quest) o un build WebGL de escritorio sin soporte XR. Esto cambia el checklist de UX/testing de la sección 7.

5. Compatibilidad del LiveKit Unity SDK con el target WebGL

El SDK de LiveKit para Unity usa WebRTC nativo; no hay evidencia en el repo de que ya se haya probado en un build WebGL. Hay que validarlo como spike técnico antes de comprometerlo en el checklist de voz.

6. type de objeto espacial "model3d" vs "model"

El ejemplo Swagger de POST /api/spatial-objects usa "model3d", pero el CHECK constraint de la tabla solo permite 'whiteboard' | 'file' | 'note' | 'model'. ¿Hay que actualizar el constraint SQL para agregar model3d, o corregir el ejemplo del Swagger?

7. URL de producción del web client

Ningún .md del repo documenta el dominio de Vercel del web client (solo la URL de Railway del backend está en DEPLOYMENT.md). Necesario para que Felipe sepa qué agregar a ALLOWED_ORIGINS si va a probar la integración embebida ahí.

8. Multi-instancia del backend en Railway

El estado de salas del WS bridge vive en memoria de proceso (Map en wsService.js). Si Railway llega a escalar el backend a más de una instancia, dos clientes en la "misma sala" podrían terminar en instancias distintas y nunca verse entre sí por WS (aunque sí compartirían estado vía Supabase/Liveblocks). ¿El plan de Railway actual garantiza una sola instancia?
